## PyQuest: A Text based game engine
I had written that I was intending to write a basic text based game engine. I actually started to write the same 
using Python. I had named the engine as PyQuest. Actually I should not be calling it an engine since it does only 
certain basic tasks - read the configuration file, show the menu and then exit the window(as of now).

## Choice of language

There were certain reasons for choosing Python as the language for the initial implementation. I really like the 
C and C++ programming languages, however implementing something as advanced as a game engine-esque in these 
languages felt a bit overwhelming. I have mostly used these languages to implement certain terminal based non-TUI
programs. To write something like a game engine(despite the fact that it is a text based one) still gave me the 
shivers, since I am not that confident with my implementation of the same in C/C++.

There was also the portion of the learning curve. In C I would have to go through the SDL3 library(which I intend to
do in due time) and in C++ I had earlier used Allegro and SFML. I intend to learn these libraries as well, however 
my current implementation needs to be prototyped faster. I also thought of using Go-lang, but for that I need to learn 
the language first. As of now, with Go-lang I cannot move as fast as possible as I would be able to do with C/C++ or 
for that matter Python.

## Choice of hardware

There is another thing to be considered while trying to write this game engine. Anyone who happens to land in the 
repository housing this code should be able to run this program on the simplest of hardware. They should be able to 
craft their own games with just a text editor and a some knowledge about JSON. I will detail out why I would like to 
use JSON in the next section.

Also, for development I needed a laptop which I could open and start with the development without having to shut it 
down or switch it on all the time. For this reason, I chose the M1 Air. There was one more reason for selecting the 
Apple device - I wanted to be able to write and progress while my son is sleeping or I get some time from office or 
whatever other household chores.

## Development starts

The first thing that I always do when I start a programming project is to make sure that I approach it with the 
concept of using a configuration file. I have seen in many Indie as well as AAA titles, the game developers lean 
heavily on using configuration file(s). This I know because I saw the videos of LowLevelGamer on YouTube.

I found that with the configuration file(s), one could tweak the game without having to know anything about the internals 
of the game itself. One should, though, have some knowledge and understanding about the changes that they are going to 
do. However, I have this understanding that changing the options in configuration file(s) causes the installation to 
become corrupt. I am not sure if this is the case now given the new DRM software and standards that are coming out.

So, configuration file was the first thing that had to be read. I have a fascination for INI configuration files. One 
primary reason for that is that they are simple and yet allows me to group the options under relevant sections.

Python offers a great module with which one can read the INI file and parse the data. The best part, this module 
is available with a standard Python distribution. No need to install this module separately. Unless the distribution 
is a custom compiled one, it should be present by default. In order to read and parse the INI file, one can use the 
basic starter code as follows:

```python
from configparser import ConfigParser

config_dict = {}

with open('config.ini', 'r') as config_file:
    config = ConfigParser()
    config.read(config_file)

    # Load the data into a dictionary
    config_dict = {section: dict(config.items(section)) for section in config.sections()}
```

As one can see, simply opening the file for reading and then passing the file handler to the parser is enough to 
read the data and parse the same.

Once this is done, I was sure that as of the starting project, I will be requiring only some information to be stored in the 
the configuration file. A INI file stores the data in the following format:

```ini
[section]
option = value
```

My initial configuration file contains the following data as of now:
```ini
[Display]
width = 800
height = 600
title = "PyQuest"
fullscreen = false

; Support for only single resource provided for now
[Resource]
root= resources
story = story.json
```

## Logging

Once the configuration file is completed, I needed to make sure that I have some kind of logging available. It is usually 
suggested to have the logger instance retrieved in every file using the `getLogger(__name__)` method. This might be the 
way for may projects, however there is a small problem with this approach. If the root logger is not properly configured, the 
logs will not be shown properly.
The other problem(more of a personal preference) is that I do not want to create a logger instance in every file. I would 
rather use only one single import line `from logging import info, debug, warning, error, critical` and then use these 
functions directly in the code. While testing, in case I need to have more verbose logging, I can enable the debug mode. 
**NOTE**: I did not specify the logging related configuration in the configuration file. Since, while testing, I want to 
explicitly enable the debug mode, hence I have not added the same in the configuration file.

So, in order to get the debug mode enabled, the first thing that is required is to add the argument parsing. The reason I 
like the argument parsing module is because, it is present by default in any standard Python distribution, is simple enough 
to use and automatically adds the `--help` option which specifies the usage of the program.
A simple implementation showcasing the same could be as follows:

```python
from argparse import ArgumentParser

parser = ArgumentParser(description="A basic description of the program")
parser.add_argument('--debug', action='store_true', help='Enable debug mode')
args = parser.parse_args()

# One can also change the parsed arguments into a dictionary if required
args_dict = vars(args)
```

Once the debug mode is enabled, the next portion is to make sure that the logging level is set to `DEBUG`. But even before 
setting the logging level, one needs to write the logger instance in such a way that the logger need not be imported all the 
time in every file.

My custom logging instance looks as follows:

```python
# standard modules
from logging import getLogger, Formatter, FileHandler, StreamHandler
from logging import DEBUG, INFO
from os import makedirs, sep
from datetime import datetime

# relative modules
from .constant import DEFAULT_LOG_DIR, DEFAULT_LOG_FMT


class LogScribe:
    """LogScribe class responsible for logging details."""

    def __init__(self, ilogdir: str = "", log_file_name: str = "", enable_fstream: bool = False,
                 enable_outstream: bool = True,
                 log_level_debug: bool = False) -> None:
        """
        For setting member variables.

        Args:
            ilogdir: string containing log directory path.
            enable_fstream: boolean, default set to False, \
                    enable for logging to file.
            enable_outstream: boolean, default set to True, \
                    disable for stopping logging to stdout.
            log_level_debug: boolean, default set to False, \
                    enable to see debug logs.
        """
        self._logger = getLogger()
        self._log_format = Formatter(DEFAULT_LOG_FMT)

        # Note: This is the default logging directory if not specified
        self._default_logdir = DEFAULT_LOG_DIR

        makedirs(ilogdir if len(ilogdir) > 0 else self._default_logdir,
                 exist_ok=True)

        ilogdir = f"{ilogdir}{sep}{log_file_name}" if len(log_file_name) > 0 else self._default_logdir

        self._logdir = f"{self._default_logdir}{sep}" +\
            f"{str(datetime.now().date()).replace('-', '_')}_PyQuest.log" \
            if len(ilogdir) == 0 else ilogdir

        self._fhandler = None
        self._shandler = None

        self.enable_filelogging(enable=enable_fstream)
        self.enable_streamlogging(enable=enable_outstream)

        self._logger.setLevel(DEBUG if log_level_debug else INFO)

    def update_formatter(self, log_line_fmt: str) -> None:
        """
        Update the logging format.

        Args:
            log_line_fmt: string containing the updated logging format.
        """
        for handler in self._logger.handlers:
            handler.setFormatter(Formatter(log_line_fmt))

    def enable_streamlogging(self, enable: bool) -> None:
        """
        Enable or disable stdout logging.

        Args:
            enable: boolean, set it to True tio add stdout handler.
        """
        if enable:
            self._shandler = StreamHandler()
            self._shandler.setFormatter(self._log_format)
            self._logger.addHandler(self._shandler)
        else:
            if self._shandler:
                self._logger.removeHandler(self._shandler)

    def enable_filelogging(self, enable: bool) -> None:
        """
        Enable or disable file logging.

        Args:
            enable: boolean, set it to True tio add file handler.
        """
        if enable:
            print(f"Logging to file: {self._logdir}")
            self._fhandler = FileHandler(self._logdir)
            self._fhandler.setFormatter(self._log_format)
            self._logger.addHandler(self._fhandler)
        else:
            if self._fhandler:
                self._logger.removeHandler(self._fhandler)

    def set_log_file(self, log_dir: str) -> None:
        """
        Set the log filepath.

        Args:
            log_dir : string containing the log file path.
        """
        if not isinstance(log_dir, str) or len(log_dir) == 0:
            self._logdir = f"{self._default_logdir}{sep}" +\
                f"{str(datetime.now().date()).replace('-', '_')}" +\
                "_framework.log"
        else:
            self._logdir = f"{log_dir}{sep}" +\
                    f"{str(datetime.now().date()).replace('-', '_')}" +\
                    "_framework.log"

    def set_log_level(self, log_level: int) -> None:
        """
        Set the logging level.

        Args:
            log_level: integer containing the constant
                value as per logging module.
        """
        self._logger.setLevel(log_level)
```

Once this is added, the next thing is to create an instance of this `LogScribe` class. This instance is something 
which will be updated based on the CLI arguments(via the argument parsing) and that should be it. No more imports are 
required in other files. Post that using the simple `from logging import info, ...` should do.

I always create the logger instance in the `__init__.py` file of the package. Since the typically place this logger in 
a file called `log.py` placed inside the `utility` module, I create the instance in the `__init__.py` file of the `utility` module. 
This way, when I import the utility module, I get the logger instance as well. The code for the same is as follows:

```python
from .log import LogScribe

logger = LogScribe(ilogdir="logs", log_file_name="PyQuest.log", enable_fstream=False, enable_outstream=True)
```

That's about it for the logging.

## Showing something on the screen

The initial implementation that I have done is to make sure that some text is being shown on the screen and the data of the 
Window title picked up from the configuration file is being shown on the title bar of the window. I had used `PyGame` a little
bit earlier and hence thought of using the same for this project as well.

## Why PyGame?

There were certain reasons, the most important of those are as follows:

- I have used the module before a bit for tinkering around.
- I like the approach that it is a wrapper on top of the SDL library. 
This means that I will be able to pick up certain things which the SDL
library allows and would be able to draw an analogy when I try to 
implement the same in SDL(c).
- I do not need something special since this is just a text based 
 game engine. The only things that I would require are `font` loading
 (like custom TTF fonts), playing the relevant music for specific 
 sections or scenarios.

**NOTE**: I have not yet decided how the music will be loaded and what
kind of music will be played, however I would like to allow myself or
any other user to be able to specify the kind of music to be played for 
each scenario or continue with the same music for certain scenarios.
